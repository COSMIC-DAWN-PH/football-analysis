# PLAN：球队颜色识别优化（Robust Team Color Classification）

分支：`codex/team-color-classification`
基线：`codex/robust-pitch-registration` @ f0529ec

## 1. 背景与问题

球队颜色分配链路：`main.py` → `ClubAssigner.assign_clubs()`（`club_assignment/club_assigner.py`）→ `get_player_club()` → `get_jersey_color()` → `clustering()` + `ClubAssignerModel.predict()`。

在 `output_videos/demo2-30s-test`（栗色 maroon vs 藏青 navy，阴天低照度、球员远景小目标）上，人工看视频存在大量红蓝互认。

现有实现的主要缺陷：

| # | 缺陷 | 位置 |
|---|------|------|
| A | `clustering()` 用 KMeans(2) 对 bbox 上半截取色，靠 4 个角像素投票定背景簇，再 `player_cluster = 1 - bg_cluster`；角像素 2:2 平票、球员占满裁剪区、裁剪区以草皮/阴影为主时，取到的"球衣色"是阴影草、皮肤或混合色 | `club_assigner.py:80-111` |
| B | `apply_mask()` 绿色去除逻辑反了：统计的是"非绿像素占比"，裁剪区大部分是背景（小球员、远距离——本视频常态）时直接返回原图不去草皮；球员占比 >8% 才去背景，正好相反 | `club_assigner.py:47-78` |
| C | 分类用裸 RGB 欧氏距离最近质心；maroon (120,37,66) 与 navy (31,72,127) 都是暗色，光照/阴影使提取色跨越决策边界，且无饱和度/亮度归一化、无红色 hue wrap-around 处理 | `club_assigner.py:216-235` |
| D | `club_by_track` 把首帧分类结果缓存整个视频，首帧出错则全程错 | `club_assigner.py:32, 189-197` |
| E | 采样区域是 bbox 上半截整块，包含头部皮肤、手臂、背景，球衣像素占比极低 | `club_assigner.py:151-154` |

**结论：这是颜色提取与分类设计问题，不是 YOLO 检测/跟踪模型权重问题**（bbox 置信度 0.7-0.87，大小合理）。YOLO 仅负责检测与跟踪，颜色分配完全由上述经典视觉逻辑决定。

诊断参考数据（demo2-30s-test 实测，仅作诊断，非验收口径）：
- 球员躯干 hue 直方图呈双峰：H≈108（蓝/藏青，22K 像素）、H≈169（红/栗色，16K 像素），与用户参考色换算（navy RGB (31,72,127) → OpenCV H≈107，maroon RGB (120,37,66) → H≈170）一致；
- 现有 pipeline 提取色大量为近黑垃圾值，如 (0,4,12)、(4,1,3)、(3,7,18)，与真实球衣无关；
- 逐帧重复提取同一球员的球衣色，26/239 帧（10.9%）与自身多数票不一致，说明提取极不稳定；
- 用 hue 双峰分组作临时对照时，36 个颜色特征可靠的球员中约 42% 与 pipeline 分配不一致——该数字仅表明问题严重程度，不作为验收 ground truth。

## 2. 目标

- 两个暗色队服（本视频场景）下红蓝互认显著减少，以人工标注验证集为准；
- 亮色/常规场景不回归；
- 门将（is_goalkeeper 路径）同步受益；
- 现有测试全绿；CPU/OpenVINO 开销可控。

## 3. 工作方式：单阶段推进 + 独立验证门（强制）

### 3.1 硬性规则

1. **一次只做一个 Phase**，不合并多个优化；每个 Phase 单独提交（commit），便于回退与对比。
2. 每个 Phase 开始前记录基线指标，完成后用**同一套评估数据与指标**对比，看是否真实提高。
3. 每个 Phase 完成后，必须由**与实现模型不同的独立模型**复核：
   - 实现方为 `gpt-5.6-luna` → 由 `kimi-k2.7-code` 验证；
   - 实现方为 `kimi-k2.7-code` → 由 `gpt-5.6-luna` 验证；
   - 其他实现方同样遵守"实现与验证必须不同模型"原则。
4. 验证模型**不得只读实现方的结论**：必须独立运行评估脚本、或编写独立的检查脚本复算指标，并复核代码 diff。
5. 验证模型必须给出明确裁决：**通过 / 不通过 + 理由**。不通过 → 修复或回退，留在当前 Phase 重新验证，不得推进下一 Phase。
6. 全部 Phase 完成后，两个模型（kimi-k2.7-code、gpt-5.6-luna）各做一次独立交叉复核，均通过才算整体完成。
7. 每一步推进（含验证结果）记录到本计划文档的「推进记录」小节。

### 3.2 评估口径（所有 Phase 共用，前后一致）

- **主口径：人工标注验证集**。从 demo2-30s-test 中选取一批**清晰、无遮挡、可无歧义判定**的球员 crop（人工标注红/蓝），排除遮挡、过暗、出界、无法判定样本。标注集与标注规则先定稿并随分支提交，验收与验证均以此为准。
- 辅助指标（同数据同脚本计算）：
  1. 红→蓝、蓝→红双向混淆矩阵（分别计数）；
  2. balanced accuracy（两队召回率的平均）；
  3. 逐 track 时序稳定性（track 最终队名与其各帧多数票的一致率、翻转次数）；
  4. 有效分类覆盖率（被给出队名的球员占比，衡量"宁缺毋滥"是否过度）；
  5. 处理耗时（端到端速度变化）。
- 工具：`tools/eval_team_colors.py`（Phase 0 落地），输入标注集 + tracks JSONL + 视频，输出上述指标的 JSON 报告，供实现方与验证模型共用。
- 之前的 hue 双峰 42% 仅作为诊断参考，**不作为验收标准**。

## 4. 方案：三层改造（提取 → 分类 → 时序）

核心思想：**不追求提取绝对球衣色**。每帧把所有球员的颜色特征聚成两组（无监督），再用参考色把组映射到球队，最后按 track 多帧投票定队。

### Phase 0 — 评估基础设施与人工标注集（先做）

- 生成 demo2-30s-test 的清晰球员 crop 集，人工标注红/蓝并定稿（排除无法判定样本），提交到分支（如 `eval/labeled_crops.json` + 标注规则说明）；
- 落地 `tools/eval_team_colors.py`，跑出现有 pipeline 的基线指标并记录（作为后续所有 Phase 的对比基线）。

### Phase 1 — 修颜色提取（替换 `clustering()` + `apply_mask()`，修缺陷 A/B/E）

- 采样区域：只取 bbox 躯干中心条带（横向 20%~80%，纵向 30%~60%），避开头部（皮肤）、腿部、bbox 边缘背景污染；
- 掩码：无条件去除绿色草皮（HSV 范围，去掉现有反逻辑的 `green_threshold` 分支）+ 过滤低饱和/过暗像素（阴影 S<60 或 V<50）；
- 取色：对保留像素取中位 hue（或 KMeans 后选饱和度最高簇），输出 hue/饱和度统计 + 有效像素数；
- 置信度：有效像素 < 30 → 本帧该球员返回 `None`，不参与分类（宁缺毋滥）。
- 验收：独立模型验证门（见 3.1），通过后单独 commit，再进 Phase 2。

### Phase 2 — 全帧无监督聚类 + 参考色只做组映射（替换 `ClubAssignerModel.predict`，修缺陷 C）

- 每帧收集所有有效球员的 hue，用 sin/cos 编码做 KMeans(2)（正确处理红色 0/180 wrap-around）；
- 两组 → 用参考色 hue（用户配置 maroon≈170、navy≈107）距离映射到两个球队名；
- 帧内有效球员 < 4 时退化到逐个最近质心分类（HSV 距离，含饱和度/亮度加权）；
- 参考色仅作"组→队名"提示，不再当硬分类标准（相机白平衡/光照会偏移用户填的 RGB）。
- 验收：独立模型验证门，通过后单独 commit，再进 Phase 3。

### Phase 3 — 时序投票替代首帧锁定（替换 `club_by_track`，修缺陷 D）

- 每个 track 维护投票计数器（`collections.Counter`），每帧（或每 k 帧）投票一次；
- 采样满 N 票（如 30）取多数值定队；定队后继续投票以吸收漂移，或按置信度锁定（待实现时权衡计算量）；
- 错一两帧不再影响整个视频。
- 验收：独立模型验证门，通过后单独 commit。

### Phase 4 — 终验

- `tests/` 新增合成测试：两个暗色队服 + 阴影/草皮污染，验证分组正确性与时序投票稳定性；现有 `pytest` 全绿；
- 最终指标报告（Phase 0~3 全程对比表）；
- kimi-k2.7-code 与 gpt-5.6-luna 各一次独立交叉复核，均通过后整体完成。

## 6. 验收标准

1. 人工标注验证集上 balanced accuracy 显著高于基线（Phase 0 基线值），且红→蓝、蓝→红两个方向的误判都减少（不允许"一侧变好一侧变差"的净零）；
2. 每个 Phase 均有独立模型验证通过的记录（见 3.1）；
3. 有效分类覆盖率下降 ≤ 5 个百分点（防"宁缺毋滥"过度）；
4. 现有 `pytest` 全绿；
5. 端到端处理速度下降 ≤ 20%；
6. 最终两个模型交叉复核均通过。

## 7. 风险与对策

- **单帧内一队人数 <2 或全被遮挡** → Phase 2 的 <4 人退化路径 + Phase 3 时序投票兜底；
- **参考色偏移大** → 组映射只用 hue 相对距离；必要时允许用户用 GUI 反查（后续）；
- **KMeans 组标签跨帧不稳定** → 组→队名映射用固定参考 hue 锚定，天然稳定；
- **性能** → 颜色提取仅在 track 前若干帧执行，达到票数后停止，总开销与原首帧提取相当；
- **标注集本身有偏** → 只收录清晰无歧义样本；标注规则先定稿再标注，避免事后改口径。
